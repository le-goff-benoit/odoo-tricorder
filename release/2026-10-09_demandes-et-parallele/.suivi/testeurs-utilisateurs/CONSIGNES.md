# Consignes communes — réception indépendante

Vous êtes un profil utilisateur de Tricorder. Objectif : comprendre et accomplir trois tâches utiles dans l’application réelle, dont un détour, une reprise ou une erreur. Commencez par observer les écrans et leurs mots ; ne lisez pas le code produit ni les rapports des autres avant vos constats. Les release Odoo sont un usage parmi d’autres. Le terminal est la conversation principale, le graphique sert à concevoir et suivre ; une seule fenêtre. Le workflow doit être réutilisable entre projets et entre agents.

## Banc strictement isolé

- Répertoire autorisé pour vos écritures : votre sous-dossier de cette campagne et vos dossiers temporaires. Vous n’êtes pas seul dans le dépôt ; ne modifiez ni le produit, ni les tests partagés, ni les travaux d’autrui. Aucun commit, build ou installation.
- Lisez `paquet.json` et utilisez `harness.cjs` : `prepare({id, output, display})`, puis `launch(manifest,{executable,executableSha256,asar,asarSha256,displayReleased:true})`. Exécutable `build-artifacts/linux-unpacked/odoo-tricorder`, ASAR `build-artifacts/linux-unpacked/resources/app.asar`, empreintes exactes du manifeste. Le paquet ne change pas pendant les neuf avis.
- Démarrage normal (aucun --workflow-studio), HOME/XDG/état/runtime/configurations fournisseurs isolés. Le harness place deux fournisseurs inertes dans un PATH fixe AVANT le démarrage du broker. N’étendez jamais ce PATH ; ne lancez aucune CLI réelle, connexion réseau, compte, messagerie ou projet client. Votre exécution ne doit jamais lire le trousseau ni les réglages réels.
- Dans le terminal de cette application isolée, contrôlez `command -v codex; codex --version; command -v claude; claude --version` AVANT toute tentative de lancement. Les chemins doivent être ceux des stubs et les deux versions contenir TRICORDER-PANEL-INERT. Arrêtez le banc si ce n’est pas le cas.
- Utilisez Playwright Electron du dépôt ; n’installez aucun outil. Les créations de projets/workflows et actions à recevoir se font par les vrais contrôles GUI. Vous pouvez lire DOM/état pour constater un résultat. Une fixture de progression utilise uniquement les commandes validées du moteur du paquet, dans votre état isolé (claim/submit/ask…), explicitement signalée dans le rapport ; jamais SQL ni JSON d’état modifiés pour forcer le passage. Une fixture ne prouve pas que l’utilisateur a réalisé le geste à sa place.
- Un dialogue natif non pilotable peut être remplacé seulement pour son chemin fictif sélectionné, en le déclarant. Ne revendiquez alors pas la réception du sélecteur natif.
- Trois parcours métier concrets, pas seulement des assertions techniques. Pour chacun : intention, gestes réellement effectués, résultat attendu/observé, réussite/partiel/échec, conséquence utilisateur. Classez séparément bug, friction, manque fonctionnel et limite du banc. Ne déduisez pas un bug d’une simulation qui ne peut pas appeler un vrai service.
- Fournisseurs inertes : n’évaluez ni la qualité d’une IA ni une release réelle. Vous pouvez évaluer compréhension du lancement, états, reprise et absence de promesse trompeuse. Une seule fenêtre applicative doit rester.
- Faites 4 à 8 captures significatives (maximum 12), OUVREZ chaque capture pour vérifier le rendu. Évitez les doublons, données privées et captures sans intérêt. Votre rapport est synthétique : 3 parcours, 3 à 6 constats priorisés avec preuves, points réussis et limites.
- Conservez script de parcours, rapport RAPPORT.md et captures dans votre sous-dossier. Appelez cleanup() à la fin et vérifiez empreintes inchangées, processus de votre banc arrêtés. Ne tuez aucun processus appartenant à un autre agent ou à l’utilisateur.

Donnez un point d’avancement au responsable lorsqu’un blocage apparaît et à la fin. Une fois le rapport rendu, ne faites pas de nouvelle exploration non demandée.
